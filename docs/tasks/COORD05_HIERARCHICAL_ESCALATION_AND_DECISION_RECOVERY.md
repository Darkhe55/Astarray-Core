# COORD-05　逐级请示、用户裁决与任务恢复

状态：待实施。归属：Core。前置依据：[任务反馈消费](COORD01_TASK_FEEDBACK_CONSUMPTION_REPAIR.md)、[直属上级关系](COMM01_ADDRESSABLE_UPPER_LAYER_AND_SINGLE_PARENT_TASK_CARD.md)、[上下文装配与回访](COORD03_CONTEXT_PACK_ASSEMBLY_AND_CLOSED_NODE_RECALL.md)。本卡通过本包的运行时、公开接口与集成测试独立验收。

## 产品裁决与范围

Worker 通过现有反馈信箱向直属上级请示。上级在管理范围内优先查阅材料、协调所属任务并作出决定；越权或确实无法决断时才逐级上报。到当前主 Agent 仍无法决断时，由它汇总影响面、候选方案和推荐理由，请用户决定。秘书已激活时经秘书处呈交，否则直接呈交用户。

本流程在主层的下一站仅限用户裁决通道，不广播、不征询或选举同级主 Agent。此限制只适用于本卡的请示路由，验收须保护既有定向通信能力。复用反馈、澄清和序列控制入口，无需向模型注册新的通信写工具。普通协调在现有权限范围内执行；一次裁决不能替代工具权限审批。

## 实施任务

| 子卡 | 实施内容 | 完成证据 |
|---|---|---|
| 05-01 责任与交接 | 核对任务分解和序列记录已有的负责范围、发布者、输入输出、依赖和版本化文档引用，仅补缺失字段。组队提示明确哪些事项能自行决定、该读哪份材料、何时请示。动态进度写入任务或交接文档。旧任务缺字段时走已验证的归属关系；无法确定时报告缺失。 | 用一组跨职责样例证明，本级有材料且有权时直接解决，缺材料时能按需读取，超出权限时向上请示。模型自述不能代替归属与权限校验。 |
| 05-02 请示契约与路由 | 在反馈契约中关联稳定请求 ID、原始发起者、项目和任务、影响步骤、问题摘要、文档 ID 与 revision。控制面从真实上下文解析唯一直属上级。每层仅追加处置结论与引用；已查范围和转交原因可追溯。用当前处理人和预期版本保护状态迁移。沿真实管理树校验方向与环，不放宽既有同级转达跳数。 | 中间层结案后上层零消息；合法多层上报可达主层；重复、并发、关系变更、缺上级或成环均有确定结果。错误可诊断且不会改投其他主 Agent。 |
| 05-03 用户待决记录 | 复用用户澄清存储，保存原请求 ID、影响面、候选项、推荐理由、受阻步骤及自由答复。按项目和原请求幂等登记，区分首次无文件、损坏与暂时不可读。并发登记或答复不可覆盖其他记录；兼容已有澄清数据及调用方。 | 重试只生成一条待决事项；并发写不同事项均保留；记录损坏时停止覆盖并给出可恢复状态。 |
| 05-04 呈交与答复 | 主 Agent 生成决策摘要，控制面读取秘书实际激活状态并选择唯一通道；先持久化待呈交记录再发送。区分待呈交、已呈交、用户已答复。秘书仅转交并关联原问题。中途启停或投递故障按同一待决 ID 恢复；通道切换前核对既有回执。 | 有、无秘书各验证一次；重复呈交、秘书切换和重启均不产生第二个逻辑问题。只有与原项目、请求及用户身份匹配的答复才进入写回。 |
| 05-05 决定写回与恢复 | 本级决定和用户裁决都写回权威任务或交接文档，记录来源、版本和影响范围。仅显式依赖该决定的步骤等待，其他可运行任务继续调度。写回与推进使用同一决定 ID；恢复前核对取消状态、依赖和文档版本。发现冲突时保留决定并进入复核。 | 已回答但尚未写回、已写回但尚未推进两个崩溃点均可恢复。重复回复最多推进一次；迟到答案不能重启已取消任务；一次通知只发给受影响任务。 |
| 05-06 上下文与观测 | 工具结果和通知只携带必要摘要、稳定引用及变更版本。按需回访材料；记录每层注入量、未变版本重复读取、产生有效证据或解除阻塞的回访，以及跨层次数。复用 T09A 口径。 | 对同一任务样例保存请求体统计与文档读取记录，验证各层未复制历史全文、无关 Agent 未收到正文，且最终执行者能取得完整决定。缓存命中率单项不能作为通过证据。 |

## 实现入口

- 责任及归属核对从 `packages/core/src/orchestration/task-decomposition-contract.ts`、`task-publisher-feedback-route.ts` 和 `task-sequence-controllers.ts` 入手。分别查清任务发布者与真实直属上级，二者不同时按管理关系上报。
- 用户问题复用 `packages/core/src/orchestration/user-clarification.ts`。当前登记会生成随机 ID，读取异常会回退为空集合；先完成 05-03 再接自动呈交。
- 秘书激活及回执参考同目录 `secretary-policy.ts`、`secretary-relay-contract.ts`。核实生产装配是否实际提供呈交、回执及用户答复入口，只有契约函数时须补齐产品接线。
- 文档持久化核对现有交接存储的作用域，按实际任务归属选用权威文档。跨范围传递引用时仍逐次验证读取权。上下文指标参见 [T09A](accepted/T09A_CONTEXT_NODE_CLOSURE_AND_RECALL_TASK_CARD.md)。

## 整卡验收

通过正常运行时创建有依赖和无依赖的两个步骤，由 Worker 在真实反馈入口发起请示，贯通中间上级、主 Agent、用户答复、文档写回和指定步骤恢复。分别运行本级解决、用户直达、秘书呈交三条路径。检查收件人、转交次数、唯一待决 ID、文档 revision、实际执行次数和请求体内容。到主层未决时同级主 Agent 收件数必须为零。并行回归既有授权定向消息测试，证明流程边界仅作用于本卡路径。

用重复投递、进程重启、秘书切换、任务取消、陈旧文档版本和损坏存储覆盖失败恢复。运行定向集成测试及 `npm run check`，记录构建版本、命令、结果和未验证环境。纯函数测试、模拟存储或仅能查询待决列表均不足以关闭本卡。
