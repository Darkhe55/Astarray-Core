# AUTH-CORE-01　工具调用授权返修任务卡

状态：待实施。本卡以本仓库的运行时、SDK、CLI 和测试独立交付。历史依据为 T06F、B6R-03 和 MERGE-01 §1.3。验收对象是通过正常派发路径执行的一次工具调用。

## 已知缺口

生产装配 application-runtime.ts 构造 ConfigurablePermissionPolicyEngine 时仅传 catalog 和 profileStore；policy-wrapper.ts 调用 decide 时缺少 action。parameter-authorization.ts 接收 toolName 却未据此过滤候选规则。引擎收到参数结果 ask 后仍可能按原基线 allow 返回。目录反向索引只含整工具映射，另存的逐 action 映射没有进入该索引。存储层用空参数试算并检查是否跳过评估，无法证明字段或条件有效。

## 实施与分项验收

1. **确定调用身份。** 从运行时注册表、实际装配的执行端口和工具 schema 解析规范工具 ID、别名、合法 action、字段类型及副作用。对无 action 的工具提供明确的整工具匹配语义。未知工具、未知 action 或无效参数须在执行前拒绝。能力目录仅提供策略默认值与分组。SDK 分别报告已注册、可执行、整工具映射和 action 映射，包括受控进程的查询与取消。
2. **落实工具基线。** 在版本化 profile 增加按工具 ID 的三态决定及按工具的细分开关，复用现有配置存储。有效基线为显式工具决定或既有能力映射得出的默认决定；另行与不可放宽的上级和运行边界求交。整工具显式 deny 立即终止。迁移旧 profile、导入导出和旧开关时保留原有效权限及 revision 冲突语义；缺失、损坏或无法无损转换时返回可诊断状态，禁止扩权。
3. **统一规则契约。** 保存与执行共用 schema 校验。校验工具、action、字段、枚举、布尔、固定值、有限数值区间和上下界。统一无 match 的整 action 规则。路径按执行器实际项目根、目标解析和平台语义匹配，覆盖分隔符、父目录、链接、目录边界及新建目标。任何无法确定的目标都不得触发放行规则。
4. **修复裁决顺序。** 先按规范工具 ID 和 action 隔离候选规则，再匹配参数；多项命中取 deny、ask、allow 中最严格者。无命中回退工具基线。以有效决定处理询问和批准；基线 allow 加规则 ask 必须进入询问。与会话、项目、专用门禁求交后才可调用执行器。返回稳定决定、来源、规则 ID 和有效版本；诊断信息遵守现有脱敏契约。
5. **接通生产和配置生命周期。** 正常装配读取同一套持久化规则，每次调用绑定一致的 profile 与规则版本。规则保存实行乐观并发控制；陈旧写入失败，失败写入不得推进版本。规则或目标变化时旧批准不能复用。放宽确认复用既有机制。按执行事实区分已保存和已生效。

## 独立验收与完成证据

通过本仓测试用注册工具和可计数执行端口，从公开设置入口保存，再经正常运行时调用。至少覆盖同 action 异工具隔离、基线 deny 加规则 allow、基线 allow 加规则 ask、批准/拒绝/超时、规则冲突、非法字段、规范路径、旧配置迁移、陈旧批准、并发保存和重启恢复。每例核对决定、来源和执行次数，拒绝及待询问均为零次。另以生产构建验证设置变更影响下一次调用并覆盖别名与逐 action 目录。运行 npm run check，记录提交版本、命令、结果及未覆盖平台。仅纯函数测试通过不可关闭本卡。

## 进展（2026-11-22，第 1 片）

已完成（本片）：

- **规则先按规范工具 ID 隔离**：`evaluateParameterAuthorization` 的匹配先比 `toolName` 再比 `action`，同 action 异工具不再串规则。
- **裁决顺序**：匹配到参数规则 ⇒ 规则决定本次调用（含 `ask`）；无命中回退工具基线。**基线 allow + 规则 ask 必须进入询问**（旧实现被基线 allow 短路吞掉）。
- **生产裁决传 action**：`PolicyWrapper` 从参数读取声明的 `action` 交给引擎，逐 action 能力映射开始生效（旧实现只有测试显式传 action 才能看到效果）。

反例与承重（先红后绿）：

| 反例 | 旧实现 |
|---|---|
| ⑪ 纯函数：同 action 异工具的规则不得套用 | 红 |
| ⑫ 引擎：基线 allow + 命中规则 ask ⇒ ask | 红 |
| ⑬ 引擎：异工具规则不生效（回归） | 绿（旧实现因基线 allow 短路） |
