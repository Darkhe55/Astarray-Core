# 决策记录：`GOAL_MODE_DEFAULT_ENABLED` 死常量二选一（2026-10-29，第 56 轮）

> **本轮只记录选项与影响，不改语义、不改代码。** 采用哪个方案属产品决定，需用户确认。

## 1. 事实（静态核对）

| 项 | 内容 |
|---|---|
| 常量定义 | `packages/core/src/orchestration/goal-contract.ts:274`：`export const GOAL_MODE_DEFAULT_ENABLED = false;` |
| 引用次数 | **全仓仅定义处 1 次**（`Select-String` 全 `packages/core/src/**` 核对） |
| 激活函数 | `resolveGoalModeActivation`（同文件 `:282`）**不读取该常量** |
| 当前"默认关闭"靠什么 | 靠调用方传 `isExplicitUserRequest` / `isAuthenticatedUser` / `isExplicitlyEnabled`；**任何调用方传 `true` 即可开启** |

## 2. 风险（为什么这算缺口）

1. **名不副实**：常量写着 `false`（"默认关闭"），但代码路径**不读它** —— 读者会以为有保护，
   实际没有。
2. **无编译期/运行期拦截**：只要装配方（或未来 UI）传 `isExplicitlyEnabled: true`，
   目标模式就开启，**与常量无关**。
3. **审计误导**：外部审计看到常量会认为"实验默认关闭已被代码保证"，但证据不成立。

## 3. 方案 A：删除常量，把"默认关"写进入参校验

**做法**
- 删除 `GOAL_MODE_DEFAULT_ENABLED`；
- `resolveGoalModeActivation` 保持现有四条件（来源=user、已认证、显式请求、显式开启）；
- 在 ADR / 代码注释里写明"**唯一开关是运行时配置**，没有编译期常量保护"。

**影响**
- ✅ 单一事实来源，不再误导审计；
- ✅ 不改任何行为（当前常量本来就没生效）；
- ⚠️ 失去"编译期一键禁用实验"的能力（若将来需要，可另加构建期开关）。

**工作量/风险**：极小；无行为变化；需同步更新 ADR-0075/0082 里对该常量的描述。

## 4. 方案 B：让激活函数读取常量作为**额外必要条件**

**做法**
- `resolveGoalModeActivation` 增加 `if (GOAL_MODE_DEFAULT_ENABLED !== true) return 关闭`；
- 或把常量改名为 `GOAL_MODE_EXPERIMENT_AVAILABLE` 以名实相符。

**影响**
- ✅ 常量真的生效：`false` 时**任何入参都无法开启**（编译期"停用开关"）；
- ⚠️ **行为变化**：当前若有人（测试/装配）依赖传参开启，会被拦下；
- ⚠️ 实验启用需要**改代码并重新构建**，不能只改配置 —— 对"实验性能力"可接受，
  但会让"用户显式开启"变成"开发者显式开启"，**与卡内"仅认证用户开启"表述不完全一致**。

**工作量/风险**：小改动，但**是语义变化**，需产品确认"开启权在谁手里"。

## 5. 建议

- 若目标是"**去掉误导、单一事实来源**" ⇒ **方案 A**（推荐；零行为变化）。
- 若目标是"**编译期彻底关死实验**" ⇒ **方案 B**，但需同时改名并更新
  "仅认证用户开启"的表述（改为"需构建期开放 + 认证用户开启"）。

**在用户确认前，本轮保持现状**（死常量保留、无行为变化），只在台账登记该决策点。
