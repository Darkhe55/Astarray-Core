# EXEC-01-02 B1（修订）：Windows 结论纠正 + Linux（WSL）实测

取代 `EXEC01_02_B1_WINDOWS_SANDBOX_VERIFICATION_2026-11-09.md` 中关于 AppContainer 的结论。
旧结论"`E_ACCESSDENIED` 必然意味着必须提权"**过度断言**，本文给出复测证据与更正。

## 1. 纠正：`E_ACCESSDENIED` 的定位（2026-11-09 复测）

用户裁决要求"在正常标准用户进程中复测并定位原因"。复测结果：

| 检查项 | 实测 | 含义 |
|---|---|---|
| 进程完整性 | `Medium Mandatory Level` | 普通（非高完整性）进程 |
| 令牌组 | 12 组；`BUILTIN\Administrators` = **"Group used for deny only"** | UAC 过滤后的**非提权管理员会话**，即普通标准用户权限 |
| 受限 SID | **无**（无 `RESTRICTED`、无 `APPLICATION PACKAGE`） | 失败**不是** Agent 沙箱的令牌限制造成 |
| `%LOCALAPPDATA%\Packages` 写入 | **可写** | 失败不是"目录不可写" |
| AppContainer 注册表键写入 | **可写** | 失败不是"注册表被挡" |
| `DeriveAppContainerSidFromAppContainerName`（不存在的名字） | **HRESULT 0x00000000，SID 非空** | userenv 的 AppContainer API **可用**，DLL/导出/调用约定都对 |
| `CreateAppContainerProfile` | `0x80070005` | 只有"建档案"这一步被拒 |

**更正后的结论**：

1. 先前"必须提权"的说法**证据不足**：我只验证了"非提权进程失败"，没有排除目录/注册表/沙箱/API 缺失等其他原因；
   现在这些原因**逐条被排除**，失败点收敛到 `CreateAppContainerProfile` 本身。
2. 仍然**未验证**的是："提权后是否成功"。本会话没有可用的交互式提权，**不能**把"提权能解决"当成已验证事实。
   按用户裁决，安装期一次性提权是**允许的设计方向**，但必须先实测确认，再对外承诺。
3. 由于 `Derive...` 在**非提权**进程可用，运行期**不需要**创建档案 ⇒ "安装期建一次、运行期只派生 SID"在技术上成立。

## 2. Linux：WSL 实测（用户裁决：Linux 用 WSL，macOS 不做）

环境：WSL2，Ubuntu 26.04，内核 `6.18.33.2-microsoft-standard-WSL2`，`bubblewrap 0.11.1`（**系统已装**，无需新增依赖）。

| 验证项 | 命令要点 | 实测结果 |
|---|---|---|
| 正常执行成立 | `bwrap --ro-bind / / --dev /dev --proc /proc /bin/echo ok` | 输出 `ok`，退出 0 ✅ |
| 网络隔离成立 | `--unshare-all` 后 `ip addr` + `getent hosts example.com` | **只有 loopback**，DNS **解析失败** ✅ |
| 宿主文件不可见 | 只 bind `/usr`/`/bin`/`/lib`/`/lib64`/一个工作目录 | `ls /home` ⇒ **No such file**；`cat $HOME/host-only.txt` ⇒ **No such file** ✅ |
| 受控目录可读 | 同上，bind `/tmp/bwprobe` → `/work` | 读到 `secret-host-data` ✅ |
| 内存上限生效 | 沙箱内 `ulimit -v 65536` + 分配 200 MB | 分配被拒，shell 存活 ✅ |
| 限额内正常执行 | `ulimit -v 512MB` + `echo` | 正常输出 ✅ |

**注意（如实）**：该 `bwrap` 构建**没有** `--rlimit-*` 选项（实测 `Unknown option --rlimit-as`），
资源限制需在启动器内用 `setrlimit`/`prlimit` 或 cgroup 施加。上述内存验证即用 `ulimit` 完成。

**边界（如实）**：WSL 内核与裸机发行版不同（命名空间支持、AppArmor 策略、cgroup 版本可能不同），
因此本结论对"WSL 环境"成立，对**裸机 Linux** 属**未验证**，需要真机复测才能声称。

## 4. 弱隔离档：不采用

用户裁决：**不批准**"网络不封"的弱隔离档作为默认或自动后备。
因此本仓库**不实现**受限令牌降级路径；默认隔离不可用时一律拒绝执行（`execution-backend-unsupported`），
保持"禁止静默退回无限制宿主执行"。

## 5. 安装期初始化的设计约束（待实现）

用户裁决允许"安装期一次性提权初始化"，但附条件：

1. **明确用户确认**：安装/首次运行必须显式告知"需要一次管理员权限来创建沙箱档案"，用户可拒绝（拒绝则不启用受控执行，而不是降级）；
2. **正确处理每用户档案**：`CreateAppContainerProfile` 是**per-user per-app**；若安装时以管理员身份运行，
   必须在**该用户上下文**下创建（或对每个使用该机器的用户各建一次），不能只给安装者的账户建；
3. **运行期保持非管理员**：运行期只调用 `DeriveAppContainerSidFromAppContainerName`（已验证非提权可用）；
4. **不得让整个客户端提权**：只有那个一次性的初始化步骤提权，主进程与所有子进程都以标准用户运行。

## 7. 资源上限的实测（2026-11-09 追加，并更正 §2 的一处过强表述）

### 7.1 更正：先前"内存上限生效"的证据不足

§2 表里"内存上限生效（`ulimit -v 65536` + 分配 200 MB ⇒ 被拒）"这条**证据不成立**：
`head -c 200000000 /dev/zero > /dev/null` 是**流式写**，不会真的占用 200 MB 地址空间，
所以它既没被挡、也证明不了限额。复测时发现该命令在两种限额下**都返回 0**。

### 7.2 真实分配下的实测（`prlimit --as` + `python3 bytearray`）

| 场景 | 结果 |
|---|---|
| `prlimit --as=64MB` + 分配 200 MB | **`MemoryError`**（被挡住）✅ |
| `prlimit --as=512MB` + 分配 20 MB | `allocated 20000000`（正常执行）✅ |

### 7.3 新发现的缺陷：`--nproc` 会让 bwrap 完全起不来

```
prlimit --as=67108864 --nproc=8 -- bwrap ...
⇒ bwrap: Creating new namespace failed: Resource temporarily unavailable
```

原因：`RLIMIT_NPROC` 按**用户**计数，不是按进程树；该用户已有进程数超过 8，
于是连创建命名空间所需的一次 fork 都失败。

**处置**：Linux 侧前缀**只用 `--as`**；进程数上限在 Linux 属**未实现**
（需要 cgroup 的 pids 控制器），Windows 侧由 Job Object 承担。已加测试钉住"不得出现 `--nproc`"。
