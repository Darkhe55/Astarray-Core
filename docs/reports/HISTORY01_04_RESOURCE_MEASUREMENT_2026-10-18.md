> **范围**：只测 **`run-history-view.ts` 的读路径**（首次可读延迟、检索耗时、列表分页、内存增量）。
> **写入代价**另记（§4）；**人工体验**仍未做，因此 `HISTORY-01-04` **不判 done**。
>
> **可复跑**：
> ```powershell
> npm run build
> node scripts/measure-run-history-view.mjs            # 1k / 10k / 50k
> node scripts/measure-run-history-view.mjs --events 1000,5000
> ```
> 脚本做法：父进程只**落盘夹具**，**每个规模各起一个子进程**只做读操作 ——
> 避免把造夹具的垃圾算进"读的内存占用"。

## 3. 结论（能说的 / 不能说的）

**能说**：
1. 5 万条事件（18.8 MB）下**首页仍 47 ms**、尾部页 40 ms —— 单页读取的**延迟**在 CLI 场景可接受；
2. 检索是**一次性 O(n) 渲染比对**：1 万条 26 ms、5 万条 111 ms；它对"人找一条旧失败"够用，
   但**不适合**当成高频索引；
3. **列表分页真的按需**：203 个 mission 只读 20 个文件（卡内 §5「按需加载」成立）。

**不能说（如实）**：
4. **`heap` 增量不是可靠的内存上界**：10k（+107 MB）反而大于 50k（+84 MB）—— 差值受 GC 时机影响，
   属采样噪声；**rss 增量更可用**（+9.4 / +153.8 / +193.5 MB），但同样不是峰值保证；
5. **分页只减少"返回条数"，不减少"读取量"**：当前实现**整份 JSON 解析进内存**，
   因此 18.8 MB 文件对应约 **0.15–0.19 GB rss** 增量。**真正的大历史需要分块存储**（见 §5），
   本卡「虚拟列表」只解决渲染、不解决读取；
6. **没有做并发/多读压力**、没有测**冷启动（OS 文件缓存未命中）**、没有跨平台（仅 Windows）；
7. **没有人工体验**（卡内 §7.8 明确不得由自动测试冒充）。

## 4. 写入代价（另记，未混入上表）

`RunHistoryStore.appendEvent()` 每次都会**重写整份文档**（读 → 合并 → 原子写）⇒ 写入是 **O(n²)**：
1 千条时单次追加需重写约 372 KB，5 万条时约 18.8 MB。本轮**未测**追加耗时（避免误读为"读很慢"），
但这是**已知设计边界**：真正的大规模历史应改为**追加式分段日志 + 索引**，而不是每事件整档重写。
本报告不把该项算作通过，也不擅自改存储格式（属设计决定 + 数据迁移）。
