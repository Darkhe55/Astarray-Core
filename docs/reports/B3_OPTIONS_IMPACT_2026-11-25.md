# B3 四方案影响评估（2026-11-25）

> 背景事实（本机实测，2026-11-25）：
>
> | 会话 | `sandbox-helper.exe run … cmd /c echo` | 结果 |
> |---|---|---|
> | 管理员 | `job-assigned` + 输出 + `exit-code 0` | AppContainer 子进程创建**成功** |
> | 普通用户 | `CreateProcessW 失败: 5`（ACCESS_DENIED） | **失败** |
> | 普通用户 + `--no-appcontainer`（仅 Job） | `job-only-ok` + 0 | 成功 |
> | 普通用户 + LPAC（退出 ALL APPLICATION PACKAGES） | `UpdateProcThreadAttribute` 返回 **50**（本机不支持） | 方案不可用 |
>
> 这与 EXEC-01 卡的裁决假设冲突：卡内写的是「`init-sandbox` 是**唯一提权入口**；`run`/`probe` 不需要提权（运行期非管理员）」。
> 实测表明：**档案可以预建，但非提权父进程无法把子进程放进 AppContainer**。
> 另有一处既有缺陷：Windows 侧从未实现 `--allow-dir`（AppContainer 默认可读面极小），
> 真实执行即使能启动，也只能读容器自己的目录——本次一并纳入评估。

## 0. 评估维度

| 维度 | 含义 |
|---|---|
| 安全强度 | 是否满足 EXEC-01 的真实隔离反例：读宿主凭据 / 网络 / 路径逃逸 / 子进程绕过 |
| 裁决兼容 | 与「客户端整体不提权、运行期非管理员」是否一致 |
| 实现成本 | 编码 + 测试 + 文档 + 安全评审 |
| 攻击面 | 新增的提权组件本身是否成为新的越权入口 |
| 运行体验 | 用户是否需要额外操作、是否出现 UAC 弹窗 |
| 可维护性 | 跨版本 Windows 兼容、故障恢复、日志与审计 |
| 验收可行性 | 能否在干净设备上按卡内清单验收 |

## 1. 方案 A：安装期常驻 broker（服务）

**架构**

```
普通用户 CLI/运行时
   │  命名管道（ACL 仅当前用户 SID）
   ▼
sandbox-broker（安装期注册：计划任务/SYSTEM 服务，常驻）
   │  1) 校验调用方 SID / 会话 / 环境登记表
   │  2) 用**调用者的用户令牌**（不是 SYSTEM 自身）构造 AppContainer 子进程
   │  3) 施加 Job Object 限额 + 超时 + 输出管道
   ▼
AppContainer 子进程（低完整性、容器 SID、无网络 capability）
```

关键点：broker 需要 `SeTcbPrivilege`/`SeAssignPrimaryToken` 才能"以调用者身份 + AppContainer SID"建进程，
所以它必须是安装期注册的**高权限常驻进程**；但**子进程用的是普通用户令牌**，不是 SYSTEM。

**影响**

- ✅ 安全强度：与现有 AppContainer 边界一致；可顺带用 SYSTEM 权限在安装期为
  「Node 运行时目录 / 工作区快照目录」追加 AppContainer SID 的读/写 ACL（补上 `--allow-dir` 缺口）。
- ✅ 裁决兼容：运行期用户不提权；提权只发生在安装期一次。
- ⚠️ 新增攻击面：管道协议是新的信任边界。必须做：调用方 SID 校验（拒绝跨用户）、
  只接受登记过的环境/可执行文件、参数不得注入 shell、工作目录白名单、并发与速率上限、
  每次请求审计（谁在何时跑了什么）。
- ⚠️ 运维：服务/计划任务的生命周期、升级、崩溃恢复、卸载清理；Windows 版本差异（服务 vs 计划任务）。
- 运行时序：CLI 首次执行会等待 broker 就绪；broker 不在时**必须 fail-closed**（不能回退宿主直跑）。
- 成本：**3–5 人日**（协议反例 → broker 实现 → CLI 接线 → 故障注入 → 文档），另加一次安全评审。
- 验收：可在干净设备上完整跑卡内清单（断网、普通用户、真实执行）。

**最大风险**：broker 被攻破即等于本机提权。因此 broker 的代码面必须极小（不做解析、不执行 shell、
只做"校验 + 建进程 + 限额"），并且所有输入都要过登记表校验。

## 2. 方案 B：会话级提权 broker

**架构**：与 A 相同，但 broker 不是常驻服务，而是用户每次会话手动启动的一次性提权进程
（`sandbox-helper.exe serve --elevated`），CLI 通过管道连接。

**影响**

- ✅ 实现最快：复用 A 的协议与建进程逻辑，省掉服务注册/升级/卸载。
- ✅ 安全强度：若同样"用调用者令牌 + AppContainer"，与 A 等价。
- ❌ 裁决冲突：每次会话需要用户主动提权一次（UAC）；"客户端整体不提权"不再成立，
  需要改写裁决文字（例如"运行期可按需一次提权，需显式确认"）。
- ⚠️ 体验：用户多一步操作；忘记启动 ⇒ 执行被拒（fail-closed，不会静默降级）。
- ⚠️ 风险：如果为了省事让 broker 直接用**管理员令牌**建 AppContainer 子进程，
  子进程会带上管理员身份上下文（虽然仍受容器 SID 限制），**削弱最小权限**，不建议。
- 成本：**0.5–1 人日**（在 A 的协议基础上砍服务部分）。
- 适用：先打通产品链路、内部测试；后续替换为 A（协议不变，只换宿主）。

## 3. 方案 C：换隔离原语（受限令牌 + Low IL + Job，不用 AppContainer）

**架构**：`CreateRestrictedToken` + `TokenIntegrityLevel=Low` + Job Object；
必要时再用 `SaferComputeTokenFromLevel`。仍然不提权。

**影响**

- ❌ 安全强度不达标：Low IL 只限制**写**（no-write-up），**不限制读**——
  沙箱进程仍能读用户目录里的凭据文件，无法通过 EXEC-01 的反例（"读取宿主凭据必须失败"）。
- ❌ 网络：没有 AppContainer capability 边界，也没有 WFP 过滤器（需要管理员）⇒ 默认可联网，
  违反卡内"网络不封的弱隔离档不批准"。
- ✅ 兼容裁决：不需要提权，运行期非管理员可行。
- ✅ 成本低：1–2 人日。
- ⚠️ 验收：只能通过"能跑脚本"的部分，通不过隔离反例 ⇒ 不能标 B3 完成，只能作为**降级档**并明确标注。
- 结论：**除非你明确接受"隔离强度下降、网络不封"，否则不建议**。

## 4. 方案 D：维持 fail-closed（不实现非提权执行）

**架构**：现状 + 明确的用户提示：Windows 受控执行需要安装期初始化且需要提权父进程；
不满足时一律 `execution-backend-unsupported`，绝不回退宿主直跑。

**影响**

- ✅ 安全：没有新攻击面；不会假装隔离。
- ✅ 成本：0。
- ❌ 产品能力：Windows 上"真实受控执行"长期不可用；依赖执行的任务（devolve 的 processExecution、
  runIntegrationTestCommand 等）在 Windows 上永远被拒。
- ❌ 目标：B3/B5 长期 blocked，内部用户测试只能覆盖非执行能力（CLI、只读面、mock 运行时）。
- ✅ 验收：可如实记录"Windows 受控执行未交付"，不阻塞其他项。

## 5. 对比矩阵

| 维度 | A 服务 broker | B 会话 broker | C 换原语 | D fail-closed |
|---|---|---|---|---|
| 真实隔离（AppContainer） | ✅ | ✅ | ❌ | — |
| 读凭据/网络/逃逸反例 | ✅ 可过 | ✅ 可过 | ❌ 读不设防 | — |
| 运行期不提权 | ✅ | ❌（每会话一次） | ✅ | ✅ |
| 新增攻击面 | 中（管道/服务） | 中（管道） | 低 | 无 |
| 实现成本 | 3–5 人日 | 0.5–1 人日 | 1–2 人日 | 0 |
| Windows 产品可用 | ✅ | ✅（需用户操作） | ⚠️ 降级档 | ❌ |
| 可维护性 | 中（服务生命周期） | 高 | 高 | 高 |
| 卡内验收 | 可完整验收 | 可完整验收 | 不能过隔离反例 | 记录 blocked |

## 6. 推荐

1. **首选 A**：唯一同时满足「运行期不提权」与「真实 AppContainer 隔离」的方案；
   也是唯一能顺带补上 `--allow-dir`（安装期 ACL 授予）的方案。
2. **若想先打通链路**：先做 **B**（复用 A 的协议与建进程代码），但要同时改写裁决文字，
   并在文档里标注"临时过渡，后续替换为 A"。
3. **C 不建议**：它会让"隔离"名不副实（能读用户文件、默认联网），与卡内安全边界直接冲突。
4. **D 只在你想冻结 Windows 执行能力时选择**：安全但产品能力缺失。

## 7. 需要你拍板的 5 个点（选 A 时）

1. **broker 形态**：Windows 服务（开机自启）还是计划任务（登录自启）？
2. **子进程身份**：确认"用调用者用户令牌 + AppContainer"，而不是 SYSTEM/管理员令牌；
3. **允许清单**：只允许登记过的环境（Node 运行时 + 工作区快照），还是允许任意可执行文件？
4. **管道鉴权**：只认当前交互用户 SID、拒绝跨用户/远程（命名管道默认不允许远程）；
5. **失败策略**：broker 不可用 ⇒ 一律拒绝（fail-closed），是否接受？

## 8. 选 A 的实施拆分（协议先行）

| 阶段 | 内容 | 反例 |
|---|---|---|
| A1 | 协议与端口：`SandboxBrokerClient`（请求/响应、超时、错误码） | 未授权 SID、超限请求、broker 未就绪 |
| A2 | broker 宿主（服务/计划任务）+ 管道 ACL | 跨用户连接、远程管道、重放请求 |
| A3 | 用调用者令牌 + AppContainer + Job 建进程；安装期 ACL 授予 | 越权路径、未登记命令、并发上限 |
| A4 | 运行时接线（`PlatformSandboxBackend` 优先 broker）+ fail-closed | broker 崩溃、超时、部分输出 |
| A5 | 验收：干净设备断网、普通用户、真实执行 + 全部隔离反例 | 读凭据、网络、逃逸、子进程绕过 |
